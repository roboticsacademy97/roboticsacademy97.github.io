**3 год.** Git записує історію проєкту знімками — **комітами**. Кожен коміт пам'ятає, що змінилося, хто, коли і навіщо. До будь-якого знімка можна повернутися, а експеримент вести в окремій **гілці**, не ламаючи робочу версію.

Сьогодні працюємо лише на своєму комп'ютері: без GitHub і без інтернету.

## Налаштування (один раз)

```bash
git config --global user.name "Іван П."
git config --global user.email "ivan-p@ra97.invalid"
git config --global init.defaultBranch main
git config --global core.editor nano
git config --list --global
```

Ім'я і пошта потрапляють у **кожен** коміт назавжди. Пиши ім'я і першу літеру прізвища, а справжню пошту не вказуй: репозиторій колись може стати публічним. Домен `.invalid` спеціально зарезервований для адрес, яких не існує. Коли заведеш GitHub, візьмеш адресу виду `…@users.noreply.github.com`, яку він дає.

## Три місця для файлу

1. **Робоча тека** — файли, як ти їх бачиш і редагуєш.
2. **Індекс** (staging area) — що піде в наступний коміт. Туди кладе `git add`.
3. **Репозиторій** — збережені коміти в прихованій теці `.git`. Туди записує `git commit`.

Індекс потрібен, щоб з п'яти змінених файлів закомітити лише ті два, що стосуються однієї зміни.

## Перший репозиторій

```bash
mkdir ~/zhurnal && cd ~/zhurnal
git init
printf '# Журнал лабораторних\n' > README.md
git status                    # README.md — untracked: Git його бачить, але не стежить
git add README.md
git status                    # тепер — у індексі, готовий до коміту
git commit -m "Додати README журналу"
git log                       # історія: хеш, автор, дата, повідомлення
git log --oneline             # коротко
```

**`git status` — твоя головна команда.** Не знаєш, що відбувається, — спитай status. Він ще й підказує наступні команди.

## Що змінилося: diff

```bash
printf '\nЛабораторні ФІЗ-експрес, блок 1.\n' >> README.md
git diff                      # зміни в робочій теці, ще не в індексі
git add README.md
git diff --staged             # зміни в індексі, які підуть у коміт
git commit -m "Описати, що лежить у журналі"
git show                      # останній коміт разом зі змінами
```

## Відкат

| Ситуація | Команда |
| --- | --- |
| зіпсував файл, ще не робив `add` — повернути як в останньому коміті | `git restore файл` |
| додав у індекс зайве — прибрати з індексу, зміни лишаються у файлі | `git restore --staged файл` |
| помилка в повідомленні останнього коміту (ще ні з ким не ділився) | `git commit --amend` |
| скасувати старий коміт, не переписуючи історію | `git revert <хеш>` |

`git restore файл` затирає незакомічені зміни **без вороття**. Перед ним подивись `git diff`.

## Хороший коміт

- **Одна логічна зміна** — один коміт. «Прогноз струму» і «виправив опечатку в README» — два коміти.
- **Повідомлення** коротке (до 60 символів), українською, каже, що зроблено: «Прогноз струму для трьох резисторів», «Серія вимірів з резистором 470 Ом».
- Погано: «оновив», «fix», «asdf», «зміни», «дз». Через місяць ти сам не зрозумієш, що там.
- Коміть часто, коли щось завершене: краще 10 маленьких комітів протягом роботи, ніж один «усе» наприкінці.

## .gitignore

Деякі файли в репозиторії не потрібні: тимчасові, згенеровані, особисті. Їх перелічують у файлі `.gitignore`:

```text
# тимчасові файли LibreOffice, поки документ відкритий
.~lock.*#
# кеш Python
__pycache__/
# мої чернетки
chernetky/
```

```bash
git add .gitignore && git commit -m "Ігнорувати тимчасові файли і чернетки"
git status --ignored          # що саме ігнорується
```

Файл, який уже закомітили, `.gitignore` не прибере: спершу `git rm --cached файл`.

## Гілки і злиття

Гілка — окрема лінія історії. На ній пробуєш, не чіпаючи `main`.

```bash
git switch -c pokhybky        # створити гілку і перейти на неї
printf '\n## Похибки\n\nПохибка АЦП: ±2 кроки.\n' >> README.md
git commit -am "Розділ про похибки"
git switch main               # README без розділу про похибки
git merge pokhybky            # влити гілку в main
git log --oneline --graph --all
git branch -d pokhybky        # гілку злито — можна видалити
```

`git commit -am` додає в індекс **уже відстежувані** змінені файли і комітить. Нові файли він не бачить — їм потрібен `git add`.

## Конфлікт

Конфлікт буває, коли дві гілки змінили **той самий рядок** по-різному. Git не вгадує, яка версія правильна, і питає тебе.

Створи конфлікт навмисно:

```bash
git switch -c variant-a
sed -i '1s/.*/# Журнал лабораторних (версія А)/' README.md
git commit -am "Заголовок: версія А"
git switch main
sed -i '1s/.*/# Журнал вимірювань/' README.md
git commit -am "Заголовок: журнал вимірювань"
git merge variant-a           # CONFLICT
```

Відкрий README.md:

```text
<<<<<<< HEAD
# Журнал вимірювань
=======
# Журнал лабораторних (версія А)
>>>>>>> variant-a
```

1. Зверху — версія поточної гілки (`HEAD`, тобто `main`), знизу — та, що вливаєш.
2. Залиш правильний варіант (або поєднай обидва) і **видали всі три рядки-маркери**.
3. `git add README.md` і `git commit` — злиття завершено. `git log --oneline --graph` покаже, як зійшлися гілки.

Передумав зливати — `git merge --abort` повертає все як було до `merge`.

## Вправи

1. Створи в `~/zhurnal` файл `plan.md` зі списком трьох справ і закоміть його. Зміни одну справу, подивись `git diff`, закоміть.
2. Зіпсуй `plan.md` (видали все) і поверни його без нового коміту.
3. Створи файл `tmp.txt`, додай його в індекс і прибери з індексу, не видаляючи файл. Потім зроби так, щоб Git його не бачив.
4. Створи гілку `ideia`, зроби в ній два коміти, поверни їх у `main` злиттям. Покажи історію з графом.
5. Влаштуй конфлікт у `plan.md` між двома гілками і розв'яжи його.
6. Знайди в `git log` коміт, у якому вперше з'явився `plan.md`, і подивись його вміст командою `git show <хеш>`.

**Поглиблено.** `git log -p plan.md` — історія одного файла зі змінами. `git blame README.md` — хто і в якому коміті змінив кожен рядок. `git stash` — відкласти незакомічені зміни, щоб переключитися на іншу гілку.
